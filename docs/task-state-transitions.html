Task lifecycle.

This describes the persisted tasks.status lifecycle in the current source checkout. The CLI and TUI expose the transitions below; lifecycle changes and their corresponding event records are committed together.

Why Reopen appears on a New task

#

The current Ctrl-G menu hides Reopen for error and blocked, but also shows it for new. That visibility rule is broader than the valid transition: a New task cannot reopen. Confirming it with either y or Y opens an action error and leaves the task unchanged. This is a menu availability mismatch.

Use qqq next to claim a ready New task. Reopen returns previously started or finished work to New; it does not start work or act as a New-to-New no-op.

Queue diagnostics also use “blocked” for a new task that is not ready because of unfinished dependencies. That diagnostic does not change the task's persisted status.

Error and blocked reports require a nonblank --reason. Normal CLI reopen of an active task must prove the saved Herdr owner absent; failed discovery is not proof. A preflight error is eligible for normal reopen only when its latest event other than archive/unarchive is an error recorded by owner preflight. Manually reported errors use --set-status new to retry.

The CLI also accepts qqq edit ID --set-status new --force to return an in_progress, error, or blocked task to new without matching its owner. It still rejects new and completed; --force is invalid with other status options. The CLI does not accept --set-status in_progress or --set-status completed: claiming uses next, and completion uses --complete.

next claims only a ready, unarchived New task. When the caller already owns a task, it returns that task without another claim event. It never directly claims an Error, Blocked or Completed task; return or reopen that task to New first.

Unusual and rejected transitions
SituationCurrent behavior

Opening an action, then another worker changes the statusConfirmation uses the current database status. Force does not guarantee success: Complete rejects an already completed task, and Mark blocked requires it still be in progress.
A pending Mark error confirmation after another worker completes the taskAccepted: the underlying force-error operation also permits Completed → Error, although Mark error is hidden when opening the menu on a completed task.
A pending Reopen confirmation after the task becomes Error or BlockedAccepted by the underlying force-reopen operation. Newly opened menus offer Retry for these states.

Archived is independent of status. Archived New tasks cannot be claimed. Archive is shown on active tasks but rejects them; an unfinished task with unarchived unfinished dependents also cannot be archived. Reopen rejects archived tasks; unarchive first, or combine CLI --unarchive --reopen. Forced Complete and Mark error do not themselves unarchive a task. A completed or unarchived dependency is available for reopening, but an archived unfinished parent or prerequisite blocks it. Unfinished unarchived dependencies allow reopening to New and then keep that task from being claimed until they finish.

Rejected mutations leave status, ownership, content and history unchanged. Commands may first run owner preflight; that separate check can record an error for a proven-dead owner before the requested action is evaluated.

The menu rules live in src/tui/mod.rs (action_menu_available); transitions and their guards live in src/db.rs (claim, edit_guarded, force_complete, force_error, force_blocked, reopen_task) and src/archive.rs. CLI option mapping is in src/main.rs.

Invariants and related fields

#
  • claim_key is set only while status is in_progress; leaving that status clears it. The active claim is unique to one task.
  • Claims, releases, completions, errors, blocked reports, and reopens append an event. Error and blocked reasons are also saved as task messages.
  • Assignment metadata and the saved Herdr link remain after a task leaves in_progress; a new claim may replace the link.
  • archived is independent of status. It does not create another lifecycle state, but archived tasks cannot be claimed and active tasks cannot be archived.
  • Status transitions can be combined with supported direct edits; the status, event, and accompanying edits commit atomically.

For command syntax and TUI behavior, see the command reference, especially completion, reopening, returning or retrying work, and action confirmations.
